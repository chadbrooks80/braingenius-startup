# Vocabulary Module

## Entry contract

Vocabulary is loaded for `/learning/vocabulary/<learningId>` by `src/lib/learning-engine/initialization/loadLearningModule.ts`, where `learningId` is a real `ModVocabLearning.id` belonging to the authenticated session user (`ModVocabLearning.learnerUserId`). Exactly one module variable is required; missing, extra, unknown, or unauthorized learning identifiers become the same learner-safe route error (a missing learning and another learner's learning are indistinguishable to the learner). Ownership of the underlying `ModVocabList` is never required: a teacher/parent may own the reusable list while a different learner holds an independent `ModVocabLearning` assignment against it.

`src/learning-modules/vocabulary/settings.json` enables the shared Learning Header and declares `"subscriptionTier": ["MONTHLY", "LIFETIME", "ADMIN"]` — the exact current tiers allowed to use Vocabulary, deliberately excluding `FREE_TRIAL` and `CANCELED`. `Vocabulary` implements the shared `ActiveModule` contract and uses browser clients for the content and answer APIs.

Vocabulary owns its module layout: `src/learning-modules/vocabulary/ModuleLayout.tsx` is the required, generically named module-layout entrypoint the Learning Engine loads and wraps around the active learning window (`<ModuleLayout registerModulePanelSetters={...}><ScreenRenderer .../></ModuleLayout>`). It renders `src/learning-modules/vocabulary/module-panels/VocabularyStatusPanel.tsx` to the left of the engine-supplied `children` inside a `flex flex-1` container it owns, forwarding only the generic `registerModulePanelSetters` capability it receives from the engine. The shared engine never imports `VocabularyStatusPanel` directly.

`VocabularyStatusPanel` owns three independent React states for its Word List, Spelling, and Mastered sections (`src/learning-modules/vocabulary/module-panels/vocabularyPanelTypes.ts` defines the module-owned `VocabularyPanelDisplayWord`, `VocabularyPanelSpellingWord`, and `VocabularyStatusPanelSetters` types). Each section's visible count derives from its array's `.length`; the Spelling state intentionally stores only stable IDs, never the canonical spelling answer, so its rows always render as masked bullets. After render, one effect bundles the three real setters into a single object via `createVocabularyStatusPanelSetters()` and registers it with the engine through the injected `registerModulePanelSetters` callback, retaining the returned disposer for cleanup on unmount or callback change.

`Vocabulary`'s constructor receives the shared `LearningModuleRuntime` (`{ runPanelSetter }`) as its second argument and retains only that narrow function (never the engine instance or its private setter registry). The constructor's second parameter also accepts a directly injected `random` function for deterministic tests, falling back to `Math.random` unless a function is given; only a real runtime object wires `runPanelSetter` (direct test instantiation with an injected `random` function gets a no-op panel publisher). Vocabulary publishes all three panel arrays from the authoritative server projection immediately after `initialize()` and after every committed definition/spelling answer, using `this.runPanelSetter("setWordList"|"setSpellingWords"|"setMasteredWords", value)`.

Vocabulary access is host-owned, not module-owned: `src/app/(app)/(learning)/learning/[...learning]/page.tsx` and all three Vocabulary HTTP boundaries independently call `authorizeLearningModuleAccess("vocabulary")` before any client engine initialization, content creation, capability mutation, grading, or paid TTS usage. See [Learning Module access](../architecture/security-and-server-boundaries.md#learning-module-access).

Vocabulary owns the structured errors for a missing learning ID, an unknown/unauthorized learning ID, and unexpected extra route segments, including each local diagnostic code and safe presentation. The shared engine transports and logs those errors, treats the Vocabulary codes as opaque, and renders the supplied safe presentation without interpreting it.

## Durable progress and resume

The database is authoritative. `ModVocabWordProgress` (per `learningId`/`listWordId`) is the durable source for introduction, definition/spelling streaks and mastery, review state, and first-mastery history; `ModVocabLearning` holds cumulative graded/correct/incorrect counters and `servedCheckpointGroupCount`; `ModVocabSession` represents one durable visit; `ModVocabAttempt`/`ModVocabAttemptChoice` are the durable, exact-once-gradable question records.

Opening `/learning/vocabulary/<learningId>` calls `vocabularyLearningStore.initializeVocabularyLearning(userId, learningId)`, which: authorizes the learning, creates any missing progress rows for the list's current words (without overwriting existing progress), safely ends any prior `ACTIVE` session and expires its `ACTIVE` attempts, and starts a new session. It returns the authoritative progress/panel snapshot plus lightweight progress rows for every current list word. `VocabularyContentCapabilityStore.createManifest` uses those rows to hydrate both the in-process lesson sequencer (`VocabularyLessonState`, seeded via `VocabularyLessonHydration`) and a bounded canonical-content cache covering the learner's actual progress (the first five words for a new learning, or every word up through the highest position with recorded progress for a resumed one) — never the full list's content for a large list. The manifest response includes a compact `hydratedProgressByWordId`/`checkpointEligibleWordIdOrder`/`servedCheckpointGroupCount` payload so the browser's own `VocabularyLessonState` mirror (which decides which content type to request next) starts from the same durable state as the server, not blank progress.

Every definition/spelling question creates a durable `ACTIVE` `ModVocabAttempt` (with its offered `ModVocabAttemptChoice` rows for definition) before content is returned; the row IDs are the public opaque attempt/choice identity. Grading (`vocabularyLearningStore.commitVocabularyAnswer`) reads only that durable snapshot, and applies the attempt, word-progress, learning-counter, session-counter, and daily-practice updates together in one Prisma transaction, then returns the authoritative `VocabularyProgressSnapshot`. An exact-duplicate submission for an already-answered attempt replays its stored result without incrementing anything again; a modified duplicate is rejected. A failed write leaves the attempt retryable and never advances the lesson, mutates counters, or changes the panel.

`Vocabulary` mirrors the returned `progress` into its local `VocabularyLessonState` (server-returned fields always win) and publishes all three panel arrays via `runtime.runPanelSetter` after initialization and after every committed answer. The panel projection (`buildVocabularyPanelProjection` in `vocabularyProgressProjection.ts`) classifies the active five (first five currently unfinished words by `position`) into Word List (`!definitionMastered && !spellingMastered`) and Spelling (`definitionMastered && !spellingMastered`, masked IDs only, never word text), and Mastered from every word with `spellingMastered = true` regardless of active-five membership. Panel item IDs are derived from `(sessionId, listWordId)` via `deriveVocabularyPanelWordId` so canonical list-word IDs never reach the browser as React keys, while staying stable within one visit and changing on the next.

Word Search checkpoints are served durably: `vocabularyLearningStore.serveNextVocabularyCheckpointGroup` recomputes the next earned-but-unserved group from first-mastery order (`selectNextVocabularyCheckpointGroup`) and increments `ModVocabLearning.servedCheckpointGroupCount` only when a new group is actually served, so a repeated read of the same checkpoint capability (already cached by the capability store) or a page refresh can never re-count or repeat it.

## Database-backed content loading and the active pool

Canonical word content (`word`, `definition`, examples, etc.) comes from `ModVocabList`/`ModVocabListWord`, queried through the module-owned `vocabularyListStore.ts` repository — never a hardcoded fixture and never a second Prisma client. Progress-row existence spans the entire current list (ensured at `initializeVocabularyLearning`), but full canonical *content* stays bounded to the hydration window described above; additional words are lazily fetched into the per-lesson cache as the lesson progresses via the existing authorized `word-refill` content request (`{ contentType: "word-refill", lessonId }`), which appends the next ordered `ModVocabListWord` to both `VocabularyLessonState` and the content cache, silently ignoring a duplicate ID so a replayed or concurrent refill can never insert the same word twice. A refill triggered while the source is already exhausted returns an explicit `wordId: null`.

`VocabularyLessonState` keeps an active pool of the first five currently loaded, not-yet-spelling-mastered words and introduces loaded words in load order:

1. `definition-display`;
2. `definition-fun-fact`;
3. graded definition practice when selected.

## Practice, mastery, recap, and review

- Definition and spelling mastery are separate and each requires three consecutive correct answers (`DEFINITION_MASTERY_STREAK`/`SPELLING_MASTERY_STREAK` in `VocabularyLessonTypes.ts`).
- Before definition mastery, practice emits a multiple-choice attempt; afterward it emits spelling.
- Normal selection avoids immediate repetition when more than one candidate exists and weights less-presented words more heavily.
- Every confirmed graded answer is followed by `answer-recap`.
- Incorrect practice resets only the relevant streak.
- Spelling mastery schedules a delayed review exactly 30 confirmed graded answers later (`ModVocabLearning.gradedAnswerCount`-based, durable across sessions).
- Due reviews are ordered by due question number, then list position, and take priority over normal practice.
- A review requires a correct definition followed immediately by correct spelling. Failure resets both mastery stages, clears the review schedule, and returns the word to normal learning — but never clears `initialMasterySequence`/`firstMasteredAt`.
- After every currently loaded word is introduced *and* `totalWordCount` word descriptors have all been loaded, the state captures a finite completion-review snapshot. Future reviews created while draining that snapshot do not prevent finite completion.

Lesson Complete requires the durable active five to be empty, no due or pending review, and no unserved earned checkpoint (`isVocabularyLearningComplete`); only then does `ModVocabLearning.status` become `COMPLETED` and its session `ENDED`.

## Word Search mastery checkpoints

After the answer that first brings a word to full initial mastery, its `ModVocabWordProgress.initialMasterySequence`/`firstMasteredAt` are assigned once (durably, never re-assigned or cleared by a later review failure/re-mastery). Every time first-mastery order reaches a new multiple of five, one checkpoint group becomes eligible; it is served (and counted) the first time its content is actually built, not merely queued. A 20-word list yields four groups (1–5, 6–10, 11–15, 16–20).

The module fetches a narrow `word-search-checkpoint` content projection (`lessonId`/`capability` only) that returns exactly `WORD_SEARCH_CHECKPOINT_GROUP_SIZE` (5) plain display word strings for that group — never canonical answer records, definitions, or unrelated content; every word shown has already been correctly spelled three times in a row, so this is not a new answer-security exception. `createWordSearchCheckpointScreenRequest` uses the subject-neutral contract at `src/lib/learning-engine/word-search/wordSearchInputContract.ts` to validate normalization, ASCII letters, 2–30 character lengths, duplicates, and structural compatibility before building a `word-search` `ScreenRequest`.

The checkpoint is ungraded reinforcement: `WordSearchWindow` is rendered with `emitCompletionAction={false}`. Checkpoint advancement changes only checkpoint/progression state: it does not change mastery, correct/incorrect/graded stats, streaks, or review scheduling.

## Attempts and retry

The module keeps one active attempt. `attemptId` is the durable `ModVocabAttempt.id`; answer type, offered public choice IDs (durable `ModVocabAttemptChoice.id` values), and review flag are bound at activation. It rejects stale IDs, wrong variants, unoffered choices, duplicate pending submissions, and already answered attempts.

Submission runs `idle → pending → success` or `error → explicit retry`. A transport/server failure cancels pending state but preserves the active attempt and leaves durable state untouched. Multiple Choice and Spelling also lock duplicate window interactions. Progress changes only after validated, durably committed server feedback.

## Content and answer security

The content endpoint rotates one screen-scoped capability at a time. Teaching and recap projections expose content only for the active display. Multiple-choice content includes a durable opaque attempt ID, public question, and four shuffled public choice IDs/text values built server-side from the active pool's own definitions (widened with a bounded database query only when the active pool cannot supply three eligible distractors). Spelling omits the target word and exposes only the definition plus an opaque attempt/speech reference.

Identity is the authenticated session `userId` (never an anonymous cookie); `learningId` authorization is independently re-verified at every content, answer, and speech boundary rather than trusted once from the initial manifest request. Exact content replay can return the recorded narrow projection. Exact duplicate answer delivery can return the recorded grade; a modified duplicate is rejected.

At content-build time the server durably persists the offered public choice IDs and the correct choice/canonical spelling into `ModVocabAttempt`/`ModVocabAttemptChoice`. Grading (`vocabularyLearningStore.commitVocabularyAnswer`) reads only that durable snapshot — it never re-derives distractors or re-queries current list content during answer submission, so exact replay and duplicate-submission grading stay stable even if the underlying list content changes mid-attempt.

Canonical word data, internal IDs, accepted spellings, and grading logic remain `server-only`. Incorrect spelling feedback may reveal the correction only after confirmed grading.

## Speech

Teaching screens use the configured Google `chirp-3-hd` voice through public text requests. Spelling uses `/api/learning/vocabulary/speech` and the opaque active attempt (the durable `ModVocabAttempt.id`). The server resolves the canonical word and its speech-synthesis definition from the durable attempt row (`vocabularyLearningStore.findVocabularySpellingAttemptForSpeech`, authorized against the caller through the attempt's session/learning chain, and only while the attempt is still `ACTIVE`) and synthesizes audio; browser requests/responses do not include its written value before grading.

## Known limitations

- The screen-scoped capability chain (which content type may legally be requested next) is a bounded-lifetime, single-process cache, not itself durable. If the process restarts mid-attempt, the durably-committed answer is never lost, but the in-flight capability chain is discarded; the learner recovers by reopening the lesson, which rebuilds correct state from the database. This mirrors the pre-existing "singleton store is not suitable for multiple server instances" limitation and is unchanged by this feature.
- Reopening a learning that is already fully `COMPLETED` currently returns the same not-found presentation as a missing learning rather than an immediate Lesson Complete screen; this is a pre-existing fixture-era gap not addressed by this persistence feature.
