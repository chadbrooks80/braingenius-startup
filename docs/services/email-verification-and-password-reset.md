# Email Verification and Password Reset

## Ownership and providers

`src/lib/auth-tokens.ts` owns token generation, hashing, and durations. `src/lib/email.ts` owns Resend delivery. `src/lib/email-verification.ts` owns atomic code consumption, `src/lib/auth/verification-code-resend.ts` owns serialized replacement, and `src/lib/auth/password-reset.ts` owns reset issuance and confirmation. Routes own parsing, post-commit delivery, and public response shapes.

All routes below canonicalize their `email` field through `CanonicalEmailSchema` (`src/lib/auth/email-normalization.ts`) before any lookup, storage, or delivery — see [Email Identity](./authentication-and-accounts.md#email-identity). A casing- or whitespace-variant address always resolves to the same account.

## Email verification

Credentials registration creates a random four-digit code, stores only its SHA-256 hash, and sets a 10-minute expiry, whenever the target email currently belongs to an unverified account (newly created or pre-existing). `attemptEmailVerification()` in `src/lib/email-verification.ts` loads the latest unused code for the email and returns one identical `400` learner-safe response for no active code, expiry, five prior failed attempts, and a wrong code.

Every write is a conditional database operation keyed to one captured request timestamp: a wrong-code attempt increments `attempts` only through an `updateMany` whose filter still requires the exact code record, matching email, unused state, unexpired state, and `attempts` below the maximum, so a code a concurrent request already consumed, expired, or exhausted is left untouched. A correct code is claimed and the user is verified and advanced inside one interactive Prisma transaction, and both conditional writes must each match exactly one row or the whole transaction rolls back: the code claim's conditional filter sets `usedAt` first (so exactly one of several concurrent correct submissions can ever claim a given code), and only a successful claim proceeds to a conditional user `updateMany` requiring the matching email, database role `PARENT`, `onboardingStep` still `VERIFY_EMAIL`, and incomplete onboarding, setting `emailVerified` and advancing `VERIFY_EMAIL → WELCOME_VIDEO`. A missing user, a database `CHILD` account, an account already past `VERIFY_EMAIL` or completed, or any other zero-row match rolls the code claim back too and reports the same generic failure — it is treated as a stale/out-of-order request, not a silent success. An unexpected failure while advancing the user rolls back the code claim the same way and propagates to the caller.

`replaceVerificationCode()` serializes resend on the canonical user's Postgres row. Inside one short transaction it re-reads and requires an unverified database `PARENT` still at `VERIFY_EMAIL` with incomplete onboarding, reads the latest code, enforces the 60-second cooldown from one captured timestamp, invalidates unused codes, and creates one replacement. Replacement failure rolls invalidation back; concurrent requests produce one replacement and one post-commit delivery attempt. Unknown, malformed, verified, ineligible, and cooldown requests retain the identical generic `200 { success: true }`. Both verification routes remain `no-store`.

## Password reset

Request validates email but always returns generic success. It validates the trusted application origin before generating grant material. For an existing credentials account outside the 60-second interval, `issuePasswordResetToken()` locks and re-reads the user and latest token in one short transaction and creates at most one cryptographically random 32-byte grant (stored only as a SHA-256 hash, expiring after one hour). Concurrent requests produce one token and one post-commit delivery attempt.

The reset URL is built by `buildPasswordResetUrl()` in `src/lib/app-base-url.ts`, never by string concatenation. `resolveAppBaseUrl()` picks the first valid candidate from `NEXTAUTH_URL`, then `NEXT_PUBLIC_APP_URL`, then `http://localhost:3000` outside production; every candidate is parsed with the `URL` API, restricted to `http:`/`https:`, rejected if it carries embedded credentials, and reduced to its bare origin (a configured path, query, or fragment is dropped). `token` and `email` are appended to `/reset-password` through `URLSearchParams`. In production, if no candidate resolves, the route creates no token, sends no email, still returns the generic success response, and logs a safe configuration error containing no email, token, or environment value.

Confirmation validates email/token/password and bcrypt-hashes the proposed password before opening a transaction. `confirmPasswordReset()` locates the owner, locks that user, re-reads the owner, and conditionally claims the exact submitted hash only while unused and unexpired. The same transaction updates the password, clears `mustResetPassword`, and invalidates sibling grants. Failure after claim rolls every write back. Duplicate submissions and different active tokens for one user share the same lock, so concurrent proposed passwords have exactly one winner.

## Failure behavior and limitations

Email provider calls remain outside transactions. Provider failure logs a fixed message with no email, plaintext grant, hash, URL, credential, secret, or provider error object and does not reverse an already-committed code/token. Recovery uses the existing cooldown. Reset-request invalid JSON/input also returns success. Reset tokens are invalidated on successful use, not when a newer token is issued.
