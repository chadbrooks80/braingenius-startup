# Email Verification and Password Reset

## Ownership and providers

`src/lib/auth-tokens.ts` owns token generation, hashing, and durations. `src/lib/email.ts` lazily creates a Resend client with `RESEND_API_KEY` and sends from `EMAIL_FROM`. `src/lib/email-verification.ts` owns the atomic verification-attempt/code-consumption contract described below. The routes under `src/app/api/auth/` stay thin and own only request parsing and the public response shape.

## Email verification

Credentials registration creates a random four-digit code, stores only its SHA-256 hash, and sets a 10-minute expiry, whenever the target email currently belongs to an unverified account (newly created or pre-existing). `attemptEmailVerification()` in `src/lib/email-verification.ts` loads the latest unused code for the email and returns one identical `400` learner-safe response for no active code, expiry, five prior failed attempts, and a wrong code.

Every write is a conditional database operation keyed to one captured request timestamp: a wrong-code attempt increments `attempts` only through an `updateMany` whose filter still requires the exact code record, matching email, unused state, unexpired state, and `attempts` below the maximum, so a code a concurrent request already consumed, expired, or exhausted is left untouched. A correct code is claimed and the user is verified and advanced inside one interactive Prisma transaction, and both conditional writes must each match exactly one row or the whole transaction rolls back: the code claim's conditional filter sets `usedAt` first (so exactly one of several concurrent correct submissions can ever claim a given code), and only a successful claim proceeds to a conditional user `updateMany` requiring the matching email, database role `PARENT`, `onboardingStep` still `VERIFY_EMAIL`, and incomplete onboarding, setting `emailVerified` and advancing `VERIFY_EMAIL → WELCOME_VIDEO`. A missing user, a database `CHILD` account, an account already past `VERIFY_EMAIL` or completed, or any other zero-row match rolls the code claim back too and reports the same generic failure — it is treated as a stale/out-of-order request, not a silent success. An unexpected failure while advancing the user rolls back the code claim the same way and propagates to the caller.

Resend enforces 60 seconds since the latest code, but enforces it silently: an unknown email, an already-verified account, a cooldown-active request, and an eligible unverified account (which invalidates unused codes, creates a replacement, and attempts delivery) all return the identical generic `200 { success: true }`. Both verification and resend responses set `Cache-Control: no-store`.

## Password reset

Request validates email but always returns generic success. For an existing credentials account outside the 60-second interval it creates a cryptographically random 32-byte token, stores only the SHA-256 hash, and expires it after one hour.

The reset URL is built by `buildPasswordResetUrl()` in `src/lib/app-base-url.ts`, never by string concatenation. `resolveAppBaseUrl()` picks the first valid candidate from `NEXTAUTH_URL`, then `NEXT_PUBLIC_APP_URL`, then `http://localhost:3000` outside production; every candidate is parsed with the `URL` API, restricted to `http:`/`https:`, rejected if it carries embedded credentials, and reduced to its bare origin (a configured path, query, or fragment is dropped). `token` and `email` are appended to `/reset-password` through `URLSearchParams`. In production, if no candidate resolves, the route creates no token, sends no email, still returns the generic success response, and logs a safe configuration error containing no email, token, or environment value.

Confirmation validates email/token/password, looks up the hash, and rejects missing, expired, used, or wrong-email tokens with one safe message. On success a transaction bcrypt-hashes the new password and marks every unused token for that user used.

## Failure behavior and limitations

Email provider failures are logged and do not reverse already-created accounts/codes/tokens. This permits resend but can leave stored credentials with no delivered message. Reset-request invalid JSON/input also returns success. Reset tokens are invalidated on successful use, not when a newer token is issued.

`tests/auth/emailVerification.test.ts` covers the atomic attempt/consumption contract directly, including the exact attempt-limit boundary, wrong/correct races, a concurrent correct-and-wrong submission, rollback on a missing user, a database `CHILD` account, an already-advanced or already-completed account, a superseded code, and rollback on an unexpected failure. `tests/auth/emailVerificationRoutes.test.ts` covers the verification and resend routes at the HTTP boundary, including that a correct code for an already-advanced account now rolls back and returns the generic failure. `tests/auth/appBaseUrl.test.ts` covers the trusted-origin resolver (candidate order, malformed/non-HTTP/credentialed rejection, path/query/fragment normalization, and `URLSearchParams` escaping); `tests/auth/passwordResetRequest.test.ts` covers the request route, including the production-with-no-configured-origin case. There are no focused automated tests for the confirmation route or the Resend adapter. UI forms provide Zod validation and pending/error states, but server routes remain authoritative.
