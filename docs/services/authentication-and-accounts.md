# Authentication and Accounts

## Ownership and entrypoints

`src/auth.ts` owns NextAuth configuration. HTTP protocol entry is `/api/auth/[...nextauth]`; UI entrypoints are `/sign-in`, `/sign-up`, and onboarding/account-recovery routes. `src/proxy.ts` and `src/lib/onboarding-funnel.ts` own the current funnel redirects. Prisma models are documented in [Database Schema](../reference/database-schema.md).

## Providers and session

- Google OAuth uses `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, maps Google verification to `emailVerified`, and enables same-email account linking. The profile mapping canonicalizes the Google-verified address before it reaches the adapter and fails closed: a missing or malformed provider email throws instead of falling back to a raw, noncanonical value, so only the canonical form (or nothing) ever reaches `createUser`/`linkAccount`.
- Credentials accepts email or username plus password. An email-form login is canonicalized (see [Email Identity](#email-identity)) before lookup; a username login is looked up as-is. It uses bcrypt and rejects non-child users without verified email.
- NextAuth uses the Prisma adapter and JWT session strategy.
- JWT/session callbacks project user ID, `role`, `onboardingCompleted`, `onboardingStep`, and `mustResetPassword`. A client `session.update()` call only triggers a refresh: the JWT callback re-reads all four fields from the database for the signed token's user ID and ignores any values a caller places on the `session` payload. The session's `mustResetPassword` is an early-routing hint only — every protected boundary re-reads the database flag before actually granting or denying access.

The adapter wrapper creates a newly provisioned OAuth user, its single free-trial subscription, and `WELCOME_VIDEO` through one nested Prisma `User.create`, so none can commit without the others. It returns an explicit NextAuth `AdapterUser` shape instead of spreading a wider Prisma model through the adapter contract.

NextAuth invokes `createUser` and `linkAccount` as separate adapter callbacks, so the provider callback as a whole is not one database transaction. The customized `linkAccount` callback has its own short transaction: it inserts the provider `Account` and, for Google, conditionally verifies and advances only a database `PARENT` still unverified at `VERIFY_EMAIL` with incomplete onboarding. An already-verified, later-step, completed, or child account links without a funnel rewrite; an unexpected transition failure rolls the account insert back. A failed provider link can retry against the complete user/subscription invariant without duplicating either row.

## Email identity

`src/lib/auth/email-normalization.ts` owns the one canonicalization rule for email identity: trim surrounding whitespace, lowercase, then validate as an email. `CanonicalEmailSchema` (a Zod field) and `normalizeEmail()` (a plain function returning `string | null`) are the only two entry points; every identity lookup, storage write, and delivery target — registration, Credentials sign-in, the Google profile mapping, verification submit/resend, and both password-reset routes — uses one of them instead of an independent `.trim().toLowerCase()` copy. `attemptEmailVerification()` (the email-verification service that owns verification-code lookup/claim) normalizes its own `email` argument again internally rather than trusting that every caller already canonicalized, so a direct call with surrounding whitespace or mixed case still resolves the canonical identity instead of silently matching nothing; the HTTP route's own `CanonicalEmailSchema` validation is defense in depth on top of this, not a substitute for it. `User.email` and `EmailVerificationCode.email` are PostgreSQL `citext` columns (migration `normalize_auth_emails`), so identity comparison is case-insensitive at the database boundary too, and both columns carry a check constraint requiring the stored value to already equal its own trimmed-lowercase form — a differently-cased or padded value can never be written directly, only through the canonical helper.

## Account creation and children

Credentials sign-up validates email/password, hashes the password, creates a `PARENT` and free-trial subscription, then creates/sends a verification code. Onboarding collects profile data, plan selection, and up to two children.

Child creation requires the signed-in database `PARENT` to still be on the `CHILDREN` step with incomplete onboarding, hashes the password, then opens a transaction that takes a Postgres row lock on the parent (`lockUserRow` in `src/lib/db.ts`) before re-checking role/step/completion and the two-child limit and creating the `CHILD` plus `ParentStudent` together. The lock serializes concurrent requests for the same parent so two simultaneous creations cannot both pass the limit check. The optional `mustResetPassword` flag is stored and is now enforced end-to-end: see [Required Password Reset](#required-password-reset) below.

## Required password reset

A credentials sign-in still succeeds for a `mustResetPassword = true` account (this proves possession of the parent-issued temporary password without a second auth system), but the resulting session is restricted: every protected boundary that re-reads the database — not the JWT hint — routes the account to `/required-password-reset` before dashboard, onboarding, checkout, or paid TTS access.

`src/lib/auth/account-access.ts` exports `getAccountAccessRoute()`, the single destination decision every boundary consults: a pending reset always wins over onboarding routing. It also exports `resolveSessionAccountAccess(userId)`, the single database-authoritative "does this session's account still exist, and where does it belong" check: a session user id with no matching `User` row resolves to `{ status: "missing-account" }` so a caller can fail closed before rendering protected content, instead of only checking `mustResetPassword` and silently treating "no user" as "not reset required". `src/lib/onboarding-funnel.ts`'s `getOnboardingRoute()` is itself role-aware — a `CHILD` account always resolves to `/dashboard` rather than the parent verify-email/onboarding funnel, since a child's default `onboardingStep`/`onboardingCompleted` values have no meaning for it.

Enforcement points:

- `src/proxy.ts` makes no allow/deny or routing decision from JWT claims such as `mustResetPassword` or onboarding state at all — a stale token can neither grant protected content nor send a database-required account away from the reset page, so it can't loop against the database-authoritative pages underneath. Its only remaining decision is a pure UX shortcut: an anonymous `/dashboard` request is redirected to `/sign-in` immediately instead of waiting for the destination page to do it.
- `src/app/(app)/layout.tsx` is the database-authoritative gate shared by both `/dashboard` and the learning route group (both nest under it): it calls `resolveSessionAccountAccess()` and redirects a missing-account session to `/sign-in` (failing closed instead of rendering) or a reset-required session to `/required-password-reset`, before either group renders, while leaving anonymous requests (public learning) untouched.
- `/getting-started` (outside the `(app)` layout) re-reads the user and redirects through `getAccountAccessRoute()` before rendering any onboarding step, including redirecting a missing-account session to `/sign-in`.
- The auth-only diagnostic routes `/playground/restrict` and `/playground/users` call the same `resolveSessionAccountAccess()` gate before rendering, so a reset-required or missing-account session can reach only the reset flow or sign-in there too, not the diagnostic content.
- `createCheckoutSession` (`src/actions/checkout.ts`) and `resolveTtsEntitlement` (`src/lib/billing/user-entitlement.ts`) both deny a reset-required or missing caller directly, before any Stripe or TTS provider call — these are direct Server Action/function boundaries a client route guard cannot cover.

`src/actions/required-password-reset.ts` exports `submitRequiredPasswordReset()`, the atomic reset mutation: it authenticates via `getServerSession`, ignores every client-supplied field except the three password inputs (current, new, and a server-enforced `confirmNewPassword` that must match the new password before any hashing or mutation), re-reads the user, requires `mustResetPassword = true` and an existing credentials password, verifies the current password, rejects a new password identical to the current one, and clears the hash and flag together in one conditional `updateMany` matched on `{ id, mustResetPassword: true }` — a zero-row match (already cleared, or a concurrent winner) is treated as `recovery`, not success. Every rejection reason (wrong current password, same-as-current new password, mismatched confirmation, or a stale/concurrent update) returns the identical generic result. On success the client calls `session.update()` with no arguments, then `router.replace()` (not `push`) to the returned destination, so Back cannot return to the completed reset form.

An ordinary email-token password reset (`/api/auth/password-reset/confirm`) also clears `mustResetPassword` in the same transaction as the password change, so a mustResetPassword account that has an email is never permanently trapped behind the required-reset screen if it recovers through the normal forgot-password flow instead.

## Sign-in return path

`src/lib/auth-return-path.ts` exports `sanitizeReturnPath`, a pure helper that turns the untrusted `callbackUrl` search parameter on `/sign-in` into a safe, root-relative, same-origin path. It rejects absolute and protocol-relative URLs, non-HTTP schemes, raw and percent-encoded backslash/slash/dot-segment confusion, control characters, malformed percent-encoding, and self-referential `/sign-in` destinations, falling back to `/dashboard` for anything rejected, missing, or blank. `/sign-in` reads the parameter once and uses the single sanitized result for Google `signIn`, Credentials `signIn`, and the successful `router.push`.

## Funnel and route gating

Order is `VERIFY_EMAIL → WELCOME_VIDEO → PROFILE → PLAN → CHILDREN → COMPLETE`. `getOnboardingRoute` maps verified incomplete users to `/getting-started` and completed users to `/dashboard`.

Every parent onboarding transition is database-authoritative: `advanceParentOnboardingStep` in `src/lib/onboarding-funnel.ts` performs one conditional `updateMany` matched on the signed-in user ID, database role `PARENT`, the action's required stored step, and `onboardingCompleted = false`. A caller-supplied or JWT-cached step is never enough on its own — only a row that still matches all four conditions advances, and profile fields are written by the same conditional call as the `PROFILE → PLAN` transition so they succeed or fail together. A zero-row match returns a typed `recovery` result carrying the caller's actual current-state destination (`resolveRecoveryRoute`) instead of advancing; `requireParentAtStep` provides the equivalent read-only gate for username lookup, suggestion, and child creation. This makes duplicate submissions, stale tabs, concurrent requests, and completed accounts all safe: at most one of two concurrent requests from the same step can succeed, and a rejected request never moves the funnel.

`/getting-started` performs a server session/user check and verifies the calculated target route itself; the proxy no longer participates in that decision (see [Required Password Reset](#required-password-reset)). An anonymous `/dashboard` or `/dashboard/...` request is redirected by the proxy to `/sign-in` with the requested path sanitized into the existing `callbackUrl` return-path contract — the proxy's only remaining route decision. `src/app/(app)/dashboard/layout.tsx` independently redirects a missing/invalid session to `/sign-in`, so the boundary holds even for a nested dashboard page reached outside the proxy matcher (now just `/dashboard/:path*`). The learning route is not in the proxy matcher, but `src/app/(app)/layout.tsx` wraps both dashboard and the learning route group and does not require a session — it only acts when one exists, so anonymous public learning stays public.

## Validation, side effects, and errors

Zod validates browser forms and server mutations, while server session checks establish identity. User-facing failures are generally safe result objects. Some server logs include action names and raw unexpected error objects; they do not intentionally log passwords.

Registration (`registerUser`) and the two email-verification routes (`/api/auth/verify-email-code`, `/api/auth/resend-verification-code`) return identical public responses regardless of whether the target email belongs to an existing, verified, unverified, rate-limited, or absent account; only syntax validation (malformed email, short password, malformed request body) is distinguishable. See [Server Actions](../reference/server-actions.md) and [API Routes](../reference/api-routes.md).

## Tests and limitations

`tests/auth/emailNormalization.test.ts` covers canonicalization and rejection; `tests/auth/credentialsSignIn.test.ts` covers Credentials lookup and verification rules; and `tests/auth/googleProfileMapping.test.ts` covers Google's canonical, fail-closed profile mapping. `tests/auth/oauthAdapterAtomicity.test.ts` covers successful user/trial/funnel provisioning, forced nested-write rollback, duplicate create retry, transactional provider linking, forced transition rollback, preservation of later-step/verified/child state, provider uniqueness, and adapter-compatible return values. `tests/auth/requiredPasswordReset.test.ts` covers the separate required-reset action. `tests/auth/passwordResetConfirm.test.ts` covers exact token claiming, sibling invalidation, forced rollback after each material write, and duplicate/concurrent one-winner behavior, including different active tokens and proposed passwords for one user.

`tests/auth/appLayoutAccountGate.test.ts` covers the real `src/app/(app)/layout.tsx` boundary directly: an anonymous request renders children untouched, a session whose `User` row no longer exists fails closed to `/sign-in` instead of rendering, a reset-required account is redirected to `/required-password-reset`, and a cleared account renders normally. `tests/auth/playgroundAccountGate.test.ts` covers the same four outcomes (anonymous, missing-account, reset-required, cleared) at both `/playground/restrict` and `/playground/users`. `tests/auth/proxyRouting.test.ts` covers `src/proxy.ts` directly against a real `NextRequest`, with `next-auth/jwt`'s `getToken` faked: an anonymous `/dashboard` request redirects to `/sign-in` with the path preserved in `callbackUrl`, an anonymous request to any other route passes through, and an authenticated request to `/dashboard` or `/required-password-reset` always passes through with no proxy-level redirect regardless of stale `mustResetPassword`/onboarding token claims in either direction — proving the proxy can no longer form the two-way redirect loop a stale JWT previously could.

`tests/auth/onboardingFunnel.test.ts` and `tests/auth/onboardingActions.test.ts` cover the preserved conditional transitions and locked child creation. `tests/auth/emailVerification.test.ts` covers the preserved atomic consumption path, while `tests/auth/emailVerificationRoutes.test.ts`, `tests/auth/passwordResetRequest.test.ts`, and `tests/auth/passwordResetConfirm.test.ts` cover the repaired replacement/issuance/confirmation boundaries. The adapter callbacks are tested directly without a Google network round trip; a full OAuth session would still require a real provider callback or prohibited test-only bypass. `tests/auth/atomicAuthDatabase.integration.test.ts` is the disposable-PostgreSQL serialization/rollback/deadlock harness and refuses to run unless the existing `DATABASE_URL` is local and unmistakably test-named.

`tests/billing/userEntitlement.test.ts` covers `resolveTtsEntitlement()` denying a reset-required caller for both direct and inherited entitlement, and `tests/api/ttsRoute.test.ts`/`tests/api/vocabularySpeechRoute.test.ts` prove a non-entitled resolver result (the same `granted: false` a reset-required caller produces) is denied at the route boundary before any provider call. `tests/billing/checkoutSession.test.ts` covers `createCheckoutSession()` directly against a faked Stripe client: an unauthenticated caller, an invalid plan, a missing-account session, and a reset-required account are all rejected with zero Stripe `checkout.sessions.create` calls, while an eligible account creates exactly one session and returns its url; a missing session url and a simulated Stripe failure both return the same generic error.

The Stage 4 Phase 2 disposable-database migration proof (success fixture, collision fixture, and rollback verification for `normalize_auth_emails`) was run directly against two throwaway databases created and dropped on the configured Postgres server for this task, seeded with synthetic non-production fixtures — see the Phase 2 implementation report for the full sanitized result. It is not a repeatable automated test in this repository, since it requires provisioning and tearing down a real disposable database rather than an in-memory fake.
